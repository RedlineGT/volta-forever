# Changes

## Unreleased

### Fixed

- `CUDA_MODULE_LOADING=EAGER`: cuBLAS 12.9, cuBLASLt, cuSPARSE, cuSOLVER and cuDNN 9.10 (its CUDA 12 build) start again through the layer, reached directly or through the forwarding libraries. Under eager loading the CUDA 12 runtime that they carry asks for the module of every fat binary at its start and gave up at the first lookup that failed: one of cuBLAS 12.9's images has ten grouped GEMM kernels for sm_80 that the layer does not translate, so `cublasCreate`, `cublasLtCreate`, `cusparseCreate` and `cusolverDnCreate` failed, and cuDNN 9.10's first operation. As NVIDIA's driver does for an image without code for the GPU, the layer now gives no module (209) under eager loading for an image with a kernel it refuses, and for an image it made from one without code for the V100 when the caller has code for the V100 of its own; their kernels stay given by `cuLibraryGetKernel`. A program of the CUDA 12 runtime whose own fat binary has a refused kernel starts without the kernels of that fat binary under eager loading. `LIMITS.md` says what eager loading costs through the layer.
- A kernel that requires its block size (PTX `.reqntid`; Triton writes it for every kernel) whose usual translation took more registers than that block allows on a V100 was given anyway, and Triton stopped before launching it (`OutOfResources: threads, Required: 512, Hardware limit: 384`). Such a kernel is now translated within that block's registers, or, when no translation fits, refused for its registers so that the PTX its cubin keeps runs.
- A kernel whose `redux.sync` takes its member mask from a register set to all ones before labels of the line tables and written again later (Triton's code for sm_80) was refused; the mask is now taken from the `mov` that reaches the instruction.
- Triton kernels with `ldmatrix` at a variable of shared memory (`[global_smem]`, in some of its reductions and grouped GEMMs) were refused on both routes; the PTX route now runs them (the machine code of it, `LDSM [RZ]`, stays refused and the PTX kept in the cubin runs instead).
- Strata's CUDA 13 engine on a two-GPU layer split no longer stops on its first request (issue #3): a kernel of a library that the layer compiles lazily, and that only reads lookup tables of its module (initialized data of internal linkage whose address no function stores, passes, compares or gives back), is compiled alone with a copy of them instead of with the whole module, which the driver compiled inside the engine's first graph capture. While such a copy is loaded, the program is not given that table by name (`cuLibraryGetGlobal`, `cuModuleGetGlobal` on a module of the library, and with them `cudaMemcpyToSymbol`, `cudaMemcpyFromSymbol` and `cudaGetSymbolAddress`): error 801 (`CUDA_ERROR_NOT_SUPPORTED`), where NVIDIA's driver gives it, and a line says why. A table asked for before such a kernel is given.

### Changed

- PTX: an asynchronous copy whose amount register is chosen between nothing and the whole size (Triton's pipelined loads) is one predicated load instead of a byte loop behind a branch: Triton's pipelined fp16 GEMMs at capability 8.0 run 1.3-1.6x faster on a V100, with the same results.
- PTX: two FP16 tensor-core products with f32 accumulators that share their A, both operands loaded by plain `ldmatrix`, are computed together on Volta's tensor cores (half the instructions). The results are the same bits as before: Triton's 1-stage fp16 GEMMs at capability 8.0 run 1.3-1.5x faster on a V100, and up to 10x where the old code spilled. `VF_PAIRS=0` now turns this off as well as the machine-code pairs.
- The documents say what the Triton campaign shows: `README.md` and `LIMITS.md` describe Triton's machine code as validated on a corpus (3,516 configurations of 20 kernels and 241 cases of vLLM's and SGLang's kernels, on a V100 and by the independent validator), not on every kernel a program may make.

### Added

- Opt-in bf16 cuBLAS variants (`forward/bf16tc/`): with `VF_CUBLAS_BF16_SKINNY=1`, bf16 products of 2 to 16 columns (fewer than 32 when small) with fp32 accumulation are computed by a kernel of the layer, with cuBLAS 12.9's bits, where 12.9 runs its sequential kernel (a rule of the shape, the layout, the alignment and the workspace, measured over 266,195 configurations; elsewhere the call goes to 12.9); with `VF_CUBLAS_BF16_TC=1`, larger bf16 products that are not captured in a CUDA graph also run on Volta's fp16 tensor cores, with exact scaling to fp16, fixed slices of k of 256 and a fallback for the rows and columns that do not convert exactly, differing from 12.9's in the last bits. Both are off by default, and the default forwarding libraries are 0.1.3's bytes. `cublasGemmEx[_64]`, `cublasGemmStridedBatchedEx[_64]` of one matrix and `cublasLtMatmul` are served; everything else goes to cuBLAS 12.9 as it is. The launcher maps both cuBLAS names to the variants or neither, and refuses to run when they are not all installed; `vf doctor` reports them. The kernels are compiled from the project's source into a checked-in sm_70 fat binary (`scripts/build-bf16-kernels.sh`). `docs/emulations.md` (section 11) states the arithmetic, `LIMITS.md` the limits.

### Tests

- `tests/gpu/triton.sh`, a differential test of Triton's kernels (translated machine code and retargeted PTX against Triton's interpreter, and against each other), and the corpus behind it (3,516 generated cases, 241 cases of vLLM's and SGLang's kernels).
- `tests/gpu/run.sh`: cases for the pairs of the PTX lowering (`pairs-adversarial`, `pairs-divergent-branch`, `pairs-divergent-loop`, `trans-order`), the copy of a chosen amount (`chosen-copy`), the required block size (`cubin-required-block-within`, `cubin-required-block-over`), `redux.sync` with a mask that reaches it (`ptx-reduction-mask-reaching`), `ldmatrix` at a variable (`ptx-ldmatrix-variable`, `cubin-ldmatrix-variable`), and lookup tables asked for by name, through NVIDIA's driver and through the layer (`tables-*`, `tests/gpu/tables.py`); `tests/proxy/readonly_tables.py` checks the tables that a kernel compiled alone copies.
- Validator: late reads of registers the translation borrows are checked; matrix loads at level 3 are not objected to for the whole function any more.
- Validator: `data_overwritten` no longer objects to a write under the complement of a store's guard, on the same predicate, which nothing between them writes (`ptxas` writes so: 1,270 objections in 14 cubins of the held-out corpus), and follows the register on for the lanes where the store ran; rule D takes a register put away at the instruction (room) for the lane of a product at level 3 (1,443 objections in 12 cubins); a register put away under a guard is objected to (it passed). Five controls more (`complement_rewritten`, `complement_same`, `room_guarded_away`, `room_lane_unsaid`, `room_lane_first`), and `tests/sass/controls.sh` takes two more cubins of the held-out corpus. `tests/sass/heldout-validate.sh` ends with status 1 when a translation has problems. With these rules: the held-out corpus at 0 problems in 3,105 of its 3,108 cubins (the other three are read by neither translator), PyTorch's 475 and Triton's 4,308 and 334 cubins at 0.
- `tests/forward/bf16.sh` (in the CI): the bf16 cuBLAS variants generated from stand-ins and their runtime against stand-ins for the driver and cuBLAS, each control failing at the check it breaks; `tests/gpu/forward-bf16.sh`: the variants on a V100 (bits against cuBLAS 12.9, the tensor-core path's error, graphs, capture modes, threads, lifetimes, the lazy setup, cuBLASLt's algorithms and workspaces, an output layer of 151,936 rows); `scripts/build-bf16-kernels.sh --check` rebuilds the checked-in fat binary.
- Eager loading: `tests/proxy/library_entries.py` and `tests/proxy/driver_capability.py` (no module under eager loading for a library with a refused kernel, or made from one without code for the V100, for a caller with code of its own), `tests/gpu/run.sh` (`rt-refuse-*`, `runtime-12.9-eager`, `runtime-13.5-cublas-forwarded-eager`) and `tests/gpu/forward.sh` (five forwarding libraries under `CUDA_MODULE_LOADING=EAGER`).

## 0.1.3 (2026-11-23)

### Fixed

- Machine code translated from sm_75 could store wrong values when a store of a register came just before an `ldmatrix` into that register: the translation wrote the load's destinations before the store had read them. Triton's fp32 `tl.dot` kernels gave wrong results, different from one run to the next, at the default settings. Present in 0.1.2 and earlier.
- With `VF_CAPABILITY` at 8.0 or more, PyTorch computed wrong results with no error, and from 9.0 faulted the GPU: it chose kernels that its sm_75 machine code has only as stubs. Callers are now told no later generation than the code they are given (PyTorch, cuDNN, cuFFT, cuSOLVER and the CUDA runtime they use: 7.5), with a line that says so; a program whose code is PTX for the generation asked is told what was asked, as before. `VF_CAPABILITY_ALL=1` restores the old answer.
- With `VF_CAPABILITY` at 8.0 or more, what a caller is told is lowered until the code given for it lowers it no more: given PTX for sm_75, it is told 7.5; given PTX for sm_80, or the PTX that sm_80 cubins retain, at most 8.0; given PTX for sm_90, at most 9.0. A program told 7.5 is given the sm_75 code of every image it loads, no longer sm_80 code (the PTX that sm_80 cubins retain, or the sm_80 PTX of another fat binary of its file).
- With `VF_CAPABILITY` at 8.0 or more, a CUDA runtime is told no later generation than the code of the libraries that use it, also through a library of theirs without GPU code, and at most 7.5 when one of them has code for sm_70. A library without GPU code of its own, beside libraries with GPU code that depend on it, is told at most 7.5 until they are loaded, then what their code allows. This general rule replaces one for cuDNN's graph library by its name; that library now follows the library of engines that the loader actually loaded.
- With `VF_CAPABILITY` at 8.0 or more, a caller whose file was replaced or removed after it was loaded is told at most 7.5.
- The capability told to a main program no longer depends on how it was started (by name through `PATH`, after a change of directory): the program is read through `/proc/self/exe`. Without `/proc`, it is classified by the path it was started by, as in 0.1.2, and its code also limits the CUDA runtime it asks through.
- The capability hooks no longer hold their lock over the loader's lock, which deadlocked a capability query made from a `dl_iterate_phdr` callback. A panic while reading a caller's GPU code sets no limit instead of ending the process.
- In a machine with a V100 and a later card, modules loaded into a context on the later card are given to the driver as the program gave them; a library (`cuLibraryLoadData`) keeps the entries of the other cards beside its code for the V100, and its kernels refused on the V100 are given in its module on the later card; `CU_FUNC_ATTRIBUTE_BINARY_VERSION` is changed to the capability told only for code on the V100.
- A refused or failed kernel lookup (`cuModuleGetFunction`, `cuLibraryGetKernel`) leaves NULL in the handle, as NVIDIA's driver does for a name it does not have, also in deferred libraries. A refusal is still error 218, also for a lookup that waited while its kernel was being refused (it was given the stub).
- Kernels that cannot run on the GPU, in the inputs of the driver's linker (`cuLinkAddData`), are refused at their lookup in the image that `cuLinkComplete` makes, with the reason: also in copies of it, when it is asked for without its size, and when it is put in a fat binary of the program's own or behind a wrapper of the CUDA runtime. Its kernels with emulated instructions are announced. They used to reach the program as code that traps.
- A module or library whose unload the driver refuses, and a link whose destruction it refuses, keep their refused kernels.
- `cuLinkAddData` reads a fat binary within the size given, and passes one of size 0 to the driver as it is; a link made with `CU_JIT_TARGET` for another architecture than the V100's gets its inputs unchanged; a library load with compiler options without values goes to the driver as it is.
- libnvJitLink.so.13: the kernels that trap in a link of which other kernels run are named in the cubin it makes (a `.note.vf.refused` note), and the layer refuses them when the program asks for them, wherever that cubin is loaded (as a cubin, from a file, as an input of the driver's linker, uncompressed in a fat binary or a wrapper). A fat binary in which every kernel traps (PTX, or relocatable sm_75 machine code) is refused, as such PTX given as text was; it used to be linked into a cubin of traps.
- PTX that a cubin retains (`-lineinfo`, `-G`) is compiled again with the contractions that its machine code made: an addition that ptxas did not fuse with a multiplication (`--fmad=false`, a debug build) is not fused by the driver's compiler either. A cubin of which that cannot be told (no line table) is not compiled from its PTX.
- A process made by `fork()` that ends with `exit()` no longer hangs in the reports at exit of the layer or of libnvJitLink.so.13; these reports (`VF_STATS`, `VF_PROFILE`, the summaries) are printed only by the process that loaded the library.
- When a context is destroyed (`cuCtxDestroy`, the last `cuDevicePrimaryCtxRelease`, `cuDevicePrimaryCtxReset`, as on `cudaDeviceReset`), the layer drops what it kept of the modules of that context (adapted images, kernels, originals kept for a second translation, the second translations) instead of keeping them for the life of the process.
- Fixed races in which a module, library, link or context handle that the driver gives again, right after an unload, a link destroy or a context destroy, made the layer drop the records of the new load (its refused kernels were then given as code that traps) or give a kernel compiled for the previous load; the same in deferred libraries (an unload during a lookup, a lookup that waited across an unload and a reload) and in the second translation at launch. A second translation made for a module whose context was destroyed is no longer unloaded by its handle, and the release of a primary context decides whether it was the last before another thread's retain.
- A kernel of a lazily compiled library is given at once while another library restored from the proxy cache is being adapted, and a library restored from the cache is adapted once when several threads ask for different kernels of it at the same time.
- A write to the proxy cache that fails leaves no temporary file; temporary files left more than ten minutes before are removed at the first use of the cache, and one left by an earlier start of a container no longer makes a later write fail.
- An unload of a module waits for a launch from its second translation and for a setting given to it, instead of possibly letting them reach a function of another module.
- `cuModuleLoad` and `cuLibraryLoadFromFile` adapt a file whose path is not valid UTF-8.
- libnvJitLink.so.13: `nvJitLinkAddFile` opens the file by the bytes of its name; a name that is not valid UTF-8 was refused, or another file was linked in its place.
- A fat binary whose compressed entry announces an uncompressed size that no entry has (above 2 GB, or more than LZ4 can make of its bytes) is refused with an error instead of ending the program on a failed allocation; a zstd entry is no longer decoded past the size it announces. The proxy's cache reader no longer reserves more than its files can hold.
- libnvJitLink.so.13: `nvJitLinkCreate` with a null array of options, or a null option, returns `NVJITLINK_ERROR_INVALID_INPUT` instead of crashing; `nvJitLinkAddData` of no bytes or at a null address returns `NVJITLINK_ERROR_INVALID_INPUT` for every input type, as nvJitLink 12.9.2 does.
- `redux.sync` forms that the PTX ISA does not have (a sum of floats, bitwise operations on other types than b32, ...) make their kernel refused instead of being lowered; over a partial warp every lane reduces in the same order; a float `min` or `max` without `.NaN` over a single lane gives the canonical NaN for a NaN, as over several.
- With `VF_PROFILE`, each kernel keeps the counts of its first 64 distinct grid, block and dynamic shared memory sizes: a long-running program no longer makes the profile grow with every new launch shape.
- `vf ptxas`: ends with status 255 on the errors it finds itself, as ptxas; the assembler's messages name the user's input files instead of `/proc/self/fd/N`; `--apply-controls`, `--enable-func-clone-sc` and `--sanitize` take their value, and `-O` no longer takes the argument after it.
- The runfiles views that `vf` makes for a Bazel program are named by a fixed hash and kept under `runfiles-v2`. The program and every process it starts hold a lock on its view, and a view is removed only when nothing holds it, also across machines that share the cache over NFS; none is removed on NFS mounted with local locks or on FUSE. `runfiles-v1`, of earlier releases, is not touched.
- The launcher no longer takes a leftover of an interrupted NCCL download (`libnccl.so.2.vf-part`), or an empty `cuda-12.9.2/lib`, for the CUDA 12.9.2 libraries, which hid a toolkit found next; `vf doctor` says which CUDA 12.9.2 directory it took and why.
- `vf fetch` unpacks each archive and the NCCL runtime in a staging directory and moves them into place with a journal: a fetch that fails or is stopped leaves the previous files rather than a mix, and Ctrl-C, SIGTERM and SIGHUP stop it once the move it is making is done. After a SIGKILL or a failure during a move, the launcher refuses the directory with a message, `vf doctor` says so, and the next `vf fetch` completes the move; it also removes what an interrupted fetch left.
- `vf fetch` says which member an NCCL wheel lacks instead of ending with a Python traceback.
- Run under itself (`vf vf ...`, or after `eval "$(vf env)"`), the launcher no longer adds its `VF_AUDIT_MAP` entries again, and `vf --no-audit` (and `vf env --no-audit`) takes the layer's audit library out of an `LD_AUDIT` that already names it, which the loader otherwise loaded all the same.
- `install.sh` removes the staging directories that killed installers left more than a day before.

### Changed

- A value of `VF_CAPABILITY` that is not a capability (`8`, `sm_80`) or is below 7.0 is said, once, and not used.
- The launcher keeps the audit libraries already in `LD_AUDIT`, after its own and without its own twice; `vf doctor` shows the whole value.
- The launcher splits an inherited `LD_LIBRARY_PATH` at `;` as well as `:`, as the loader does, and leaves out its empty components (the current directory, to the loader).
- The launcher refuses a CUDA 12.9.2 directory (`--cuda12`, `VF_CUDA12`) or an installation whose path has a `:` or a `;`, at which the lists that it sets would be split.
- `install.sh` holds its downloads to HTTPS, redirections included; `VF_INSTALL_BASE` must be `https://` or `file://` (`http://` with `VF_INSTALL_ALLOW_HTTP=1`).
- `scripts/fetch-redist.py` (`vf fetch`) refuses a manifest given by an `http://` URL, and follows no redirection from HTTPS to HTTP, unless it is given `--allow-http`; an archive that aria2c fetched through such a redirection is removed.
- The documents say what 0.1.3 does: `LIMITS.md` lists its known limits first and says what `VF_CAPABILITY` does not cover; the translation of sm_80 machine code is not checked by the independent validator (`docs/validation.md`, section 8); `INSTALL.md` lists every variable that the layer, the launcher and the installer read. `README.md` says that machine code generated at run time by Triton is less widely validated than PyTorch's own kernels.
- `INSTALL.md` and `docs/emulations.md` say that `VF_BF16_TC_GROUPS`, `VF_BF16_TC_TILES` and the `tree` modes of `VF_BF16_ROW` and `VF_BF16_COLUMN` do not give the same bits from run to run when a program leaves unused operands of a product uninitialised, and that Volta's tensor cores truncate when they add.
- The SGLang guide quotes what a server started without `VF_CAPABILITY_ALL=1` prints (an out-of-memory error while the model is built), and says that with it PyTorch's own attention (`--attention-backend torch_native`) and cuDNN convolutions must not be used. Its 35B AWQ server, measured again with 0.1.3: 2,010.01 prefill and 79.55 decode tokens/s (2,016.06 / 77.33 before).

### Added

- `VF_CAPABILITY_ALL=1` tells the callers that are held to 7.5 what `VF_CAPABILITY` asks all the same, for a program that does not launch the kernels it would choose for it (the SGLang guide sets it).
- `VF_JIT_LINEINFO=1`: the launcher makes the CUDA compilers that a program runs while it runs keep the PTX of what they build (`-lineinfo` in `NVCC_APPEND_FLAGS`, never next to `-G`; `CUTE_DSL_LINEINFO=1`), which the layer compiles for the V100. It is for a program told 8.0 or later that builds kernels at run time (PyTorch extensions, FlashInfer, TileLang, CuTe DSL); `vf doctor` suggests it to such a program.
- The PTX that a cubin retains is used also when the cubin calls functions that the driver provides (`__assertfail`, `vprintf`, as Triton's bounds checks and nvcc builds with `assert` do), when the retained source declares them `.extern .func`. Such cubins for sm_80 and later were refused.
- `min` and `max` on bf16 without `.NaN` (Triton's relu on bf16 tiles), and on f16 and f16x2 with or without `.NaN`, are lowered for Volta as CUDA's `__hmin` and `__hmax` compute them below sm_80; the first had no Volta sequence and ptxas refused the others. The `.ftz` and `.xorsign.abs` half forms are refused per function.
- When the layer refuses a kernel of NCCL, it says once, at the default log level, that NCCL's CUDA 12 build is needed and that `vf fetch --only libnccl` downloads it. `LIMITS.md` and the SGLang guide say that any use of several GPUs from PyTorch (`torch.distributed`, `DataParallel`) needs it.
- `vf translate IN OUT MAP` writes `MAP.lives` beside the map, as `reference/translate.py` does, so that `reference/validate.py` can check a translation made by the layer's translator.
- With an environment made by `vf venv` activated, `vf version` and `vf doctor` say which release it runs when it is not theirs.

### Tests

- Validator: a new rule (`data_overwritten`) checks that what a store or a shuffle reads is not overwritten by arithmetic before the memory instruction has read it; it objects to the translations of the defect above, which it passed. Rule V follows the moves of uniform predicates kept in the frame (`mem: load/store UP<n>`); rule B4 is asked of every instruction of a function with a frame; rule D checks that the lane register that a sequence reads at level 3 is declared taken. Five new controls (`up_standin_l3`, `up_wrong_word_l3`, `up_no_store_l3`, `up_unwaited_l3`, `unordered`): 108 controls, 105 objected to.
- `tests/sass/controls.sh` and `reference/controls.py` fail on every cubin whose translation a control changes without an objection, apart from the cases looked at one by one where what it changed stays right, instead of only on a control objected to nowhere.
- `torch-ops.py` and `torch-models.py` read verdicts from a channel of their own, so kernel output can no longer hide or forge one; the parent takes one verdict for each case it named and started. A case that does not end within `VF_CASE_WAIT` (600 s) is stopped and counted as a CRASH. A missing or unknown verdict, or a short count, fails the run. The comparisons check shapes, types and the number of results before any arithmetic, and `torch-models.py` compares both runs of a case with the CPU. New host test `tests/gpu/torch-workers.py`, run in CI.
- `vllm.sh` stage c2 checks every sampled token against the top-k and top-p of the engine's own log-probabilities, and fails a NaN or an impossible log-probability; a stage of `vllm.sh` or `sglang.sh` takes its verdict only from the program's `verdict:` line, and passes only when the program then ends with status 0 in time; no stage passes on fewer results than prompts (new host test `tests/gpu/vllm-engine-verdicts.py`, run in CI).
- `vllm-topk-topp-run.sh` compares vLLM's sampling kernel with the same kernel run on the CPU by Triton's interpreter (18 of 18 the same), in a second pass at `VF_BORROW=5` with a cache of its own; a NaN fails the comparison, and it and its test end with a failure when a case fails.
- `launcher.sh` compares the matmul with the CPU within 1e-3 (it was 1.0), and a NaN fails it; `compare.sh` reports a reference translator job that died; `llamacpp-ops.sh` counts only the case lines; `torch-models.sh` and `torch-bench.sh` look for PyTorch under `VF_TEST_ROOT`, like the other scripts.
- New host tests: `tests/proxy/lifecycle.sh` (fork, contexts, the lazy lock, cache temporaries, file names), `link_refusals.py`, `nccl_remedy.py`, `jitlink_fork.py`; `jitlink_objects.py` also checks fat binaries whose kernels trap and file names that are not UTF-8. New GPU cases in `tests/gpu/run.sh` (126 cases), among them `stored-machine-code`, `refuse-link`, `jitlink-marked`, `cubin-embedded-import`, the products of retained PTX, the bounds of bf16 and halves, and the reductions of floats over exited and single lanes.
- The CI also runs the host tests `graph_fit.sh`, `lifecycle.sh`, `library_entries.py`, `driver_capability.py`, `link_refusals.py`, `nccl_remedy.py`, `jitlink_fork.py`, `nvml_capability.py`, `tests/forward/stack.sh`, `tests/gpu/torch-workers.py`, `tests/gpu/vllm-engine-verdicts.py`, `tests/launcher/install.py` and `tests/launcher/fetch-redist.py`, and names its actions by commit.

## 0.1.2 (2026-11-22)

- VF can fetch the CUDA 12 build of NCCL and select it for both SGLang and PyTorch. SGLang generated with the 35B model on two V100s over NVLink. A separate NCCL all-reduce passed on four V100s. The four-GPU SGLang server stopped during startup.
- Add an opt-in register allocation policy (`VF_BORROW=9`) for CUDA Graph kernels whose register use would otherwise prevent a legal block size on Volta.
- Extend BF16 and machine-code translation, preserve compatible indirect calls in standalone PTX, and adapt PTX passed to external assemblers through `vf ptxas`.
- Install releases atomically and share fetched CUDA libraries across installed versions.
- Add guides and measured prefill and decode rates for eight inference engines on V100 with quantized Qwen3.5-35B-A3B weights. See the inference engine table for each quantization and native comparison.

## 0.1.1 (2026-11-21)

- CUDA runtime libraries built with separate device compilation can now use their relocatable PTX on Volta. VF compiles independent kernels on demand and preserves cross-object calls when linking the complete library.
- Matching weak CUDA kernels and kernels with launch-supplied shared memory can be compiled individually across linked objects. Conflicting declarations still go through the device linker.
- The sm_75 machine-code translator handles uniform sign extension and mixed-register address calculations emitted by Triton.
- The PTX translator handles packed BF16 subtraction, packed FP8-to-BF16 conversion and BF16-to-FP16 conversion.
- vLLM's standard NVML backend now sees the same capability as its CUDA 13 PyTorch runtime under `vf`. Its NVML query reports 7.5 for Volta by default and honors `VF_CAPABILITY`.
- Under `vf` or `vf venv`, direct CUDA driver clients with no embedded GPU code also see 7.5 on a V100 by default. Direct clients can still read native Volta kernel binary versions. CUDA 12 runtimes keep their previous handling of explicit overrides, and other GPUs retain their physical capabilities.

## 0.1.0 (2026-11-21)

The first version made public. It runs software built with CUDA 13 on a Tesla V100 with the 580
driver:

- `libcuda.so.1`, in front of NVIDIA's driver library: PTX for later GPUs retargeted, with the
  instructions that Volta lacks rewritten (the tensor-core products of Turing, Ampere and
  Blackwell, matrix loads, bf16, FP8, FP4, block-scaled products); machine code for sm_75
  translated to sm_70 when it is loaded; kernels that cannot run refused with a reason; a cache
  of what was worked out.
- Forwarding libraries for 22 libraries of CUDA 13, served by their CUDA 12.9.2 builds; an
  nvJitLink 13 served by nvJitLink 12.9.2; an audit library for programs that open their
  libraries by path.
- `vf`, a launcher (`volta-forever` under its long name): `vf COMMAND` runs a command through
  the layer, `vf venv DIR` makes a virtual environment of Python that runs through it by
  itself, `env` prints the environment for a shell session, `fetch` downloads the CUDA 12.9.2
  libraries from NVIDIA's servers, `doctor` says what is missing; the offline tool is
  `vf-translate`, which the launcher has as `vf inspect`, `extract`, `adapt`, `translate`.
- A program can ask whether the layer is there: `volta_forever_version()` and
  `volta_forever_abi()` in `libcuda.so.1`, `VOLTA_FOREVER` in the launcher's environment.
- Tested with PyTorch 2.14.0, llama.cpp b12418, vLLM 0.34.0, SGLang 0.5.23 and ZML
  (`LIMITS.md`).

Known limits of this version are in `LIMITS.md`; how the translations are checked, and what no
check covers, in `docs/validation.md`.
