# How the layer works

A compatibility layer that lets CUDA 13 software, built for sm_75 and later and
distributed without any code for Tesla V100 (compute capability 7.0), run on V100s
with the 580 driver, the last branch that supports them.

## 1. The problem

NVIDIA removed Volta from the CUDA toolkit at version 13. The 580 driver branch is
the last that supports the V100; NVIDIA has announced that it maintains that branch
into 2028. On it, the CUDA 13.5 runtime initialises, manages memory and loads code:
there is no minimum-driver refusal. What stops CUDA 13 software on a V100 is the code
itself.

Three things fail:

1. **No kernel image.** Fat binaries built by CUDA 13 carry machine code for sm_75
   and later. The driver picks from a fat binary the entry for the GPU's architecture;
   on sm_70 nothing is picked, and the program gets
   `CUDA_ERROR_NO_BINARY_FOR_GPU` (error 209). When a fat binary holds PTX alongside
   the machine code, its `.target` says sm_75 or later and its `.version` is 9.x; the
   driver's JIT on the 580 branch accepts PTX up to ISA 9.0 and refuses a `.target`
   above the device.

2. **Libraries refuse the GPU.** `cublasCreate` reads the compute capability with
   `cuDeviceGetAttribute` and returns `CUBLAS_STATUS_ARCH_MISMATCH` (8) on sm_70.
   The CUDA 13 math libraries hold no Volta kernels.

3. **JIT compilers refuse sm_70.** nvcc 13, ptxas 13, NVRTC 13 and nvJitLink 13 do
   not accept `sm_70` as a target.

A stock PyTorch 2.14.0 wheel for CUDA 13 carries only sm_75 machine code, no PTX.
llama.cpp's official build carries PTX alongside its machine code. ZML carries its
own CUDA 13 libraries and opens them by absolute path. Each needs a different
combination of the routes below.


## 2. The parts

The layer is three libraries, a command-line tool and 22 generated forwarding
libraries, built from ten Rust crates.

```
 program (CUDA 13)
   |
   +--> libcuda.so.1  (the proxy)        crates/vf-proxy
   |      answers runtime lookups, adapts every image the program loads:
   |        PTX retargeted and lowered    crates/vf-ptx
   |        machine code translated       crates/vf-sass (tables: crates/vf-tables)
   |        fat binaries parsed           crates/vf-fatbin
   |        the decisions                 crates/vf-adapt
   |
   +--> libvf_audit.so  (audit)        crates/vf-audit
   |      substitutes libraries by file name through the loader's audit interface
   |
   +--> libnvJitLink.so.13  (adapter)    crates/vf-jitlink
   |      presents the CUDA 13 API, served by nvJitLink 12.9.2
   |
   +--> dist/forward/                     crates/vf-fwdgen
          22 forwarding libraries: the CUDA 13 names served by CUDA 12.9.2
```

| Crate | Installed as | What it does |
|---|---|---|
| `vf-proxy` | `dist/lib/libcuda.so.1` | Takes the place of NVIDIA's user-mode driver library. Forwards every function to it; intercepts the few through which code reaches the driver. |
| `vf-adapt` | (library used by the proxy) | Decides what to load in place of an image that carries nothing for the GPU. |
| `vf-ptx` | (library) | Parses PTX text, rewrites Turing-only instructions for Volta (`lower/`), analyses which kernels can be compiled alone (`deps.rs`), lists what each kernel runs of emulated instructions (`emulated.rs`), handles functions the compiler refuses (`refused.rs`). |
| `vf-fatbin` | (library) | Parses and builds fat binaries: entries, compression (zstd, LZ4), cubin headers. |
| `vf-sass` | (library) | Translates sm_75 and supported sm_80 machine code to sm_70, function by function (`translate/`). |
| `vf-tables` | (library) | Volta, Turing and selected Ampere instruction forms as tables, generated by `reference/generate.py`. A crate of its own because its licence is (LGPL 2.1; see `docs/translator.md`, "The instruction tables"). |
| `vf-audit` | `dist/lib/libvf_audit.so` | An `LD_AUDIT` library that intercepts the loader's search and substitutes libraries by file name from a map. Can answer cuDNN's version queries. |
| `vf-jitlink` | `dist/lib/libnvJitLink.so.13` | Presents the nvJitLink 13 API. Turns `-arch=sm_75` (or higher) into `sm_70`, adapts PTX inputs the same way as the proxy, and passes everything to nvJitLink 12.9.2. |
| `vf-fwdgen` | (build tool) | Reads the exports and headers of the CUDA 13 and 12.9 libraries, generates 22 forwarding libraries and verifies them. Run by `scripts/build-forwarders.sh`. |
| `vf-cli` | `dist/bin/vf-translate` | The offline tool, which the launcher has as `vf inspect` (which architectures a file carries), `vf extract`, `vf adapt`, `vf translate`. |

`scripts/build.sh` builds the Rust workspace and installs the proxy, the nvJitLink
adapter, the audit library and the tool into `dist/`.
`scripts/build-forwarders.sh` generates the 22 forwarding libraries into
`dist/forward/`.


## 3. The path of a module

When a program loads GPU code, the proxy intercepts the call and decides what to give
the driver in its place.

### How the proxy sees every load

The CUDA runtime resolves driver functions through `cuGetProcAddress`, not `dlsym`.
The proxy answers these lookups with its own entry points for the functions it
intercepts; lookups of every other function return NVIDIA's own pointer, so copies,
memory management and the rest of the hot path do not pass through the proxy at all.
A kernel launch passes through an entry of the proxy that calls the driver and looks
at its answer only when that answer is a refusal (section 5).

The private tables behind `cuGetExportTable` are integrity-checked by the runtime (a
modified copy causes error 103, `cudaErrorSoftwareValidityNotEstablished`; two of the nine
that a program with PyTorch and cuFFT asks for, measured on a V100 with driver 580.178.04), so
they are forwarded untouched. Code is loaded through the public functions
(`cuLibraryLoadData`, `cuModuleLoadData` and their variants). A library may take the
functions of a module it loaded from such a table instead of `cuModuleGetFunction`: cuFFT (12.x
of CUDA 13) loads each of its kernels as a module of one function with `cuModuleLoadData`, and
enumerates the functions of the module through entry 7 of the table
`6e163fbe-b958-444d-835c-e182aff1991e` (which it asks for itself, not through its runtime), which
calls a function of cuFFT for each of them, with the module's context, the module, that function
and where it stores the handle; it then asks about the function with `cuFuncGetAttribute` and
launches it with `cuLaunchKernel` (measured on a V100 with driver 580.178.04, 2026-11-23). What
the layer refuses is refused at those public calls too (section 5).

In a machine that also has a later card, a module loaded into a context on that card
(`cuModuleLoadData` and its variants, `cuModuleLoad`, `cuLinkAddData`) is given to the
driver as the program gave it: the proxy asks the driver which device the current
context is on. A library (`cuLibraryLoadData`) is loaded for every context of the
process, the V100's included, so its code is adapted wherever it is loaded; a fat binary
keeps the entries of the other cards.

### Fat binaries and what is chosen

A program gives the driver a pointer to a fat-binary wrapper, a fat binary, a cubin
or PTX text (`crates/vf-proxy/src/images.rs`). The proxy looks at what the pointer
leads to:

- **The image already has code for sm_70**: loaded as is (the `Native` outcome).
- **The image has PTX for a later architecture**: the PTX is retargeted and lowered.
- **The image has machine code for sm_75 only** (no PTX): the machine code is
  translated to sm_70. In the default mode, if the translator refuses every entry point, VF also checks
  for complete PTX retained inside the same cubins. It retries from that source when the PTX path can
  lower every function. Modules with a working machine-code entry keep their translation.
- **The image has PTX and machine code for sm_75**: by default the PTX path is
  taken (PTX was written to be compiled for any target; machine code was written
  for one). `VF_TRANSLATE=first` reverses the preference.
- **The only image is a cubin for sm_80 or later.** NVIDIA's assembler can retain its source in
  the `.nv_debug_ptx_txt` ELF section. VF checks for a single PTX module with the same target and
  kernel names. Executables exporting additional device symbols and relocatable objects require a
  separate PTX image. Calls that the executable leaves to the driver (`__assertfail`, `vprintf`,
  `malloc`, `free`) are accepted when the retained source declares them `.extern .func`. With matching source, VF uses the same lowering and driver JIT as for ordinary
  PTX. For stripped sm_80 executables, the machine-code translator checks each function against a
  set of supported instruction forms. It converts descriptor-based global memory accesses after
  proving the descriptor on every incoming path, then uses the same register allocator, scheduler and
  Volta emitter as for Turing. A refused function is reported by name at lookup.

For a program told 8.0 (`VF_CAPABILITY=8.0`), the default policy prefers compatible Ampere
PTX, including complete PTX retained in that target's cubins. If a fat binary only supplies
stripped sm_75 and sm_80 executables, VF prefers the broader sm_75 instruction coverage, and
the program is then told 7.5, not 8.0 (section 4): told 8.0, it would launch its kernels for
sm_80, which the sm_75 code does not have. When only the stripped sm_80 image is available,
VF translates its supported functions. `VF_TRANSLATE=first` gives machine code for the
requested capability precedence.

### PTX retargeted and lowered

PTX for sm_75 or later is rewritten for sm_70 in two steps
(`crates/vf-ptx/src/lower/`, `crates/vf-adapt`):

1. **Lowering.** Instructions that Volta lacks are replaced by sequences it has. For
   example, the Ampere tensor-core product `mma.sync.aligned.m16n8k16.row.col.f32.f16`
   becomes four of Volta's `mma.sync.aligned.m8n8k4.row.col.f32.f16`, with operands
   gathered by warp shuffles and loads rearranged into the layout Volta's instruction
   takes. `tanh` is expanded. For the full list, see `docs/emulations.md`.

2. **Retargeting.** The header is rewritten: `.version` lowered to 9.0 (the driver's
   limit), `.target` to `sm_70`. The driver's JIT then compiles the text natively.

A function that uses an instruction without a Volta sequence (clusters of blocks,
Hopper's barriers, tensor maps) is made to trap. The kernels that need it are listed
and refused when the program asks for them (error 218; the reason is printed), while
the other kernels of the module load and run.

Kernels that run emulated (slower) instructions are announced on the console. The
first 20 are listed by default (`VF_EMULATION_WARNINGS`); the total is printed when
the process ends.

### Machine code translated

When a program loads an image that holds only sm_75 machine code (a stock PyTorch
wheel, NVIDIA's libraries), the proxy gives the image to the translator
(`crates/vf-sass`), which rewrites each function for sm_70 and produces a cubin the
driver accepts. Functions the translator cannot handle are left as stubs; their
kernels are refused at the lookup with the reason, the same way as PTX kernels.

For details of the translation itself, see `docs/translator.md`.

### What is refused, when, and how the program is told

A kernel that cannot run on the GPU is refused when the program asks for it
(`cuLibraryGetKernel` or `cuModuleGetFunction` returns
`CUDA_ERROR_INVALID_PTX`, 218, and writes NULL in the handle, as NVIDIA's driver does for a
name it does not have), with the reason on the console. The other kernels
of its module load and run. Module and library enumeration return the usable handles, and
the corresponding count includes only those entries.

The module of a library (`cuLibraryGetModule`) is what the CUDA 12 runtime takes the kernels of
a fat binary from, by name, one after the other; under eager loading
(`cuModuleGetLoadingMode`, from `CUDA_MODULE_LOADING`) it does so for every fat binary at its
start, and a lookup that fails there ends its initialization. Under eager loading, therefore, a
library with a refused kernel is given no module in a context on the V100
(`CUDA_ERROR_NO_BINARY_FOR_GPU`, 209, NVIDIA's answer for an image without code for the GPU,
which the runtime takes as an image to do without); its other kernels stay given by
`cuLibraryGetKernel`. Nor is a library whose image was adapted, when the caller of
`cuLibraryGetModule` has code for the V100 of its own (`callers`: it is told the real
capability and chooses that code): the CUDA 12.9 libraries would otherwise have the kernels for
later GPUs of hundreds of images compiled at their start. Under lazy loading the runtime asks
for the module at the first launch of one of its kernels, and goes on without those it is
refused: the module is given.

A program can hold a handle to a refused kernel all the same: from a private table of the
driver (above), from an enumeration made before the driver's compiler refused something of a
deferred library, or from a function the driver made for a library in a context. The function is
in the driver, made to trap, and launched it ends the context. So a launch, a kernel node of a
graph, and a question about a function or a setting of it are refused with the same 218 when
the handle is that of a refused kernel, and the driver is not called
(`crates/vf-proxy/src/guard.rs`, section 5). The driver says what a handle is
(`cuKernelGetLibrary`, `cuFuncGetModule`, and the name), which leads to the records of
refusals; a function of a module the layer does not know, which may be the module the driver made
for a library in this context, is compared with the function of that library's refused kernel of
the same name in the current context (when it is not that one, what is concluded is not kept: it
may be the kernel's function in another context, asked about while that one is not current).
The refusals of a library that is not deferred hold on the V100 only: in a context on a later
card the driver runs the library's own code.

Through the driver's linker the same holds: what was refused or emulated in each input of
`cuLinkAddData` is kept for the link, given at `cuLinkComplete` to the image the link made
(known by its length and a hash of its bytes, so that a copy of it loaded later is known
too), and dropped at `cuLinkDestroy`. Each input is adapted alone: a kernel that calls a
function of another input that cannot run is not refused, and traps when it is launched.
Inputs given with `cuLinkAddFile` are not adapted.

The first refused kernel of NCCL in a process (a name that starts with `ncclDevKernel_`,
`ncclSymkDevKernel_` or `ncclKernel_`) also makes the proxy say, at the default log level,
that NCCL's CUDA 12 build is what the program needs and that `vf fetch --only libnccl`
downloads it (`LIMITS.md`, "Several GPUs and NCCL").

There are two origins of refusal:

1. **The layer.** A PTX function uses an instruction without a Volta sequence, or the
   machine-code translator cannot handle a function. The affected functions are made
   into traps (PTX) or stubs (machine code), and the kernels that reach them through
   calls are listed.

2. **The driver's compiler.** ptxas on the 580 driver may still reject lines of the
   adapted PTX. Its error messages name the lines; the proxy replaces the functions
   that hold them and loads the image again (up to 8 rounds, with a 1 MiB message
   buffer). The kernels that need those functions join the refused set.

### Lazy kernel compilation

A module's adapted PTX may hold dozens of entry functions, but a run typically uses
one or two. The driver's JIT compiles every entry on `cuLibraryLoadData`. To avoid
compiling tens of megabytes of rewritten PTX at once, the proxy compiles each kernel
on demand (`crates/vf-proxy/src/lazy.rs`, `VF_LAZY`, on by default):

- At `cuLibraryLoadData`, the adapted PTX is kept in memory and a small stand-in
  module (header only) is loaded for a valid handle.
- At `cuLibraryGetKernel(library, name)`, a sub-module for that kernel alone is
  extracted and loaded through the driver.
- Operations that need the full module (`cuLibraryGetGlobal`, `cuLibraryGetManaged`,
  kernel count and enumeration) load the whole adapted image through the driver at that moment.

For a device-linked library, VF also reads the entry points in the linked cubin and
matches them to the relocatable PTX objects. A kernel can be compiled separately
when one object defines it, it calls no device functions and it uses no persistent
module state. Other lookups use the complete device-linked wrapper so that NVIDIA's
linker resolves external functions and shared globals. Debug strings referenced by
the extracted kernel's line information stay with it.

The soundness rule: a kernel is **independent** (can be compiled alone) when it
references no persistent variable (`.global`, `.const`) of the module, except the
string constants of `vprintf` and `__assertfail`, whose content is identical in every
copy, and read-only data. Everything else is **dependent** and served from the whole
module. The analysis is in `crates/vf-ptx/src/deps.rs`.

Read-only data is a variable whose bytes the module gives (plain data with an
initializer that names nothing, no attribute such as managed memory, alone in its
declaration), whose name the module keeps to itself (no `.visible`, `.weak`, `.extern`
or `.common`: such a name is shared state that other translation units may use) and
that no function can change: its address, or a value made from it, reaches nothing but
the address of a load and arithmetic (no store of any kind, atomic, reduction, call or
copy, no register of a function's signature, no comparison and no carry, from which
the address could be rebuilt, and no other variable's initializer). Every function of
the module is read for this: a body that the analysis cannot read, or a definition
that it does not find, leaves no variable read-only. Lookup tables are such data (the grids of llama.cpp's and
Strata's i-quants). The sub-module of a kernel that reads it holds a copy, and every
copy keeps the same bytes for as long as the program writes none; it can write one
only through an address it asks for by name. So while a sub-module holds a copy of a
variable, the program is not given that variable (`cuLibraryGetGlobal`, and
`cuModuleGetGlobal` on a module of the library): it gets `CUDA_ERROR_NOT_SUPPORTED`
(801; NVIDIA's driver gives a variable of internal linkage by its name in the PTX, so
`CUDA_ERROR_NOT_FOUND` would wrongly say that there is none), and a line at the default
log level says why. A variable that the program was given first is the whole module's,
and the kernels that read it are then served from there, also one asked for by another
thread while the whole module is being compiled for the variable.

Over llama.cpp's 149 modules (b12418, its sm_75 PTX), all 7,628 entries are
independent (7,365 before read-only data was copied); over the 52 modules of Strata's
CUDA 13 engine 0.1.64, 2,782 of 2,800 (2,081 before), the other 18 sharing variables
that they write. A first run of the demonstrator takes seconds instead of minutes.

### The cache

The proxy caches what it worked out for each image in a directory of the user
(`~/.cache/volta-forever/proxy` by default, `VF_PROXY_CACHE`), so that a later run
neither adapts nor analyses the same module again, nor translates its machine code
again (`crates/vf-proxy/src/cache.rs`).

What is cached, keyed by a 128-bit hash of the image, the adaptation policy and the
build identity of the layer:

- A **manifest**: every entry point, which can be compiled alone, which are refused
  (and why), which run emulated instructions (and how many).
- **Sub-module PTX** for each independent kernel a program actually used, as it was
  given to the driver.
- For images with machine code only, the **translation**: the whole replacement image.

What a program sees does not change: the same kernels are refused at the same call
with the same message, the same emulation warnings appear at the same moment.

The cache directory must be owned by the user and not writable by group or others
(the layer makes it with mode 0700); files are written under a temporary name of their
own (created new, mode 0600) and renamed into place; a write that fails removes its
temporary file, and the first use of the directory in a process removes those that writes
left more than ten minutes before. Each file is opened without following links and must,
as opened, be a regular file of the user. The default limit is 2 GB
(`VF_PROXY_CACHE_MAX`).

### When modules go

What the proxy keeps of a module (its adapted image, its kernels and their refusals, the
original kept for a second translation, the second translation) is dropped when the
program unloads it (`cuModuleUnload`, `cuLibraryUnload`), and when its context goes:
`cuCtxDestroy`, `cuDevicePrimaryCtxReset`, and the last `cuDevicePrimaryCtxRelease`, by
both names of each, and the last `cuCtxDetach` (an attach, `cuCtxAttach`, takes one detach more)
(`crates/vf-proxy/src/contexts.rs`). Nothing is unloaded in the driver
then: it dropped them itself. A library (`cuLibraryLoadData`) is in every context and stays
until it is unloaded; only the modules that the driver gives for it in a context go with
that context. A green context is used through the context that `cuCtxFromGreenCtx` gives for
it, and its modules go at `cuGreenCtxDestroy`. An unload waits for a launch from
the module's second translation and for a setting being given to it. What the refusal at a
launch concluded of a handle (section 5) is concluded again from the moment each of these calls
begins, and `cuGreenCtxDestroy` too, and again after it returns; what is concluded while one is
under way is not kept: once the driver has freed the handles of its functions, it may give one to
another function, in another thread, before the call returns.

The reports at exit (`VF_STATS`, `VF_PROFILE`, the summaries of emulated instructions and
of second translations) are printed by the process that loaded the layer: a child made by
`fork()` prints none, so that a child that ends with `exit()` cannot wait for ever on a
lock that another thread of its parent held at the fork. The nvJitLink adapter
(`libnvJitLink.so.13`) does the same with its summary of emulated instructions.

Measured on one Tesla V100 (driver 580.178.04): llama.cpp's 48-token generation takes
1.3 seconds with a warm cache and 6.9 seconds with a cold cache. For a stock PyTorch
2.14.0 wheel (which has only machine code), the full battery of 820 operations takes
5 to 7 seconds with a warm cache and 63 seconds without.


## 4. What a program is told about the GPU

A program chooses its kernels and launch parameters from the compute capability of
the GPU. Code built for sm_75 and later must be told a capability it has kernels for;
once told 7.5 it loads its Turing code, which the layer adapts. Code that does have
Volta kernels (the CUDA 12.9 libraries that stand in for their CUDA 13 versions) must
be told the real 7.0, so that it uses them.

The proxy answers by caller (`crates/vf-proxy/src/callers.rs`). When a program or
library queries the compute capability (`cuDeviceGetAttribute`,
`cuDeviceComputeCapability`), the hooked function reads the return address to identify
which loaded file is asking (through `dladdr`; for the main program, the file that
`/proc/self/exe` names, so that the answer does not depend on how it was started), and
classifies it:

| Caller | Told | Why |
|---|---|---|
| A file whose fat binaries hold code for sm_70 | The real 7.0 | It has native Volta code and must use it. |
| `libcudart.so.13` or later | 7.5 (default) | The CUDA 13 runtime serves programs built for sm_75 and later; the program's code starts there. |
| A file whose embedded code starts at sm_75 or later | Its lowest target (default) | The caller selects that architecture's code. |
| A readable caller with no detectable CUDA fat binary, under `vf` or `vf venv` | 7.5 (default) | Direct driver clients, including Python bindings, can load code from a separate file. |
| A CUDA 12 or older runtime | The real 7.0 by default | The runtime supports Volta directly. |
| Unidentified or unreadable caller, or one whose path now names another file than the one loaded (another inode, other program headers or notes) | The real 7.0 by default; 7.5 at most with `VF_CAPABILITY` at 8.0 or more | The proxy cannot classify its GPU code. |

On a V100, `VF_CAPABILITY=7.0`, `8.0` or `12.0` explicitly sets the answer for
direct clients, older CUDA runtimes and programs built for later GPUs. A value that is
not `<major>.<minor>`, or that is below 7.0, is not used, and the proxy says so once
when it is loaded. A caller
with embedded Volta code retains 7.0 even with an explicit override. A caller is
not told a later generation than the code it is given: when the code embedded
in its file, in a library loaded with it as a dependency (`DT_NEEDED`: the libraries
that use a CUDA runtime, and those that use these), or, for a caller without GPU code of
its own, in a library beside it that depends on it and that it may load later (as cuDNN's
graph library loads the library of its engines, also through a link to a file elsewhere; until
such a library is loaded, which file the loader takes for it is not known, and code of it to
adapt is taken to be sm_75 machine code), runs from the translation of its sm_75 machine code, or
from its PTX for sm_75 when it has none for the generation asked,
the caller is told 7.5 (8.0 for sm_80 code, when 9.0 or later is asked), and a line at
the default log level says so. The images that such a caller loads are then adapted for
what it is told: an image that also has PTX for sm_80, or sm_80 cubins that retain theirs,
is given its sm_75 code or its PTX for sm_75. PyTorch is such a program: in its sm_75 code, the
kernels it chooses for 8.0 print an error and write nothing, and some of those it
chooses for 9.0 stop the GPU. Where such a caller is told a later generation all the same
(below), a kernel whose machine code for sm_75 writes no memory, where its code for the
architecture told writes, is refused (`vf_sass::effects`). A program whose code is PTX for the generation asked (as
llama.cpp's, for sm_75, sm_80 and sm_90) is told what was asked and given its PTX for that
capability. The decision is taken when a caller first asks; a
library loaded after that is not looked at. `VF_CAPABILITY_ALL=1` tells a CUDA runtime,
and the code that uses it, what was asked all the same, for a program that does not launch the kernels it would
choose for it (the SGLang guide: SGLang selects its quantized experts from PyTorch's
capability); a library that asks for itself without that runtime (cuDNN, cuFFT, cuSOLVER)
chooses only its own kernels by the answer, and is still told what its code allows. The proxy checks the queried
device's physical major and minor before changing an answer. Other GPUs keep their
physical values, including in a mixed-device process. A code-free client using the
proxy without the launcher gets the physical capability by default.

vLLM also asks NVML for the compute capability before creating a CUDA context. Under
`vf` or `vf venv`, the audit library binds `nvmlDeviceGetCudaComputeCapability` to a
wrapper. It calls NVIDIA's function with the original device handle and, on success
for an sm_70 GPU, reports 7.5 by default or the value of `VF_CAPABILITY`, to every
caller: the limit above, by the code a caller is given, is not applied there, so told 8.0
a program that reads NVML and a CUDA runtime that is told 7.5 give it two answers. This covers
Python's `ctypes` lookup via `dlsym` and native calls through the ELF procedure
linkage table. Native clients compiled with `-fno-plt` can read the physical value
through a direct data relocation. Running outside VF or with `vf --no-audit` also
exposes the physical capability through NVML.

A program may also ask the architecture of a kernel's machine code
(`cuFuncGetAttribute`, attribute `CU_FUNC_ATTRIBUTE_BINARY_VERSION`): the backward
pass of PyTorch's attention stops when the answer is below the architecture of the
variant it chose. The driver has the layer's sm_70 code and answers 7.0. The proxy
raises the answer for a runtime or a caller with later GPU code to at least the
capability it was told. A direct client with no embedded GPU code under the
launcher gets the driver's actual kernel binary version, including 70 for a
native Volta kernel, even when its device query returns 7.5 or a configured value.

A program that wants to know what is really there can ask the layer itself
(`crates/vf-proxy/src/marker.rs`): `libcuda.so.1` has the functions
`volta_forever_version()` (the layer's version, a C string) and `volta_forever_abi()`
(the number of this interface, 1) only when it is the layer's, so that `dlsym` finds
them or does not. The symbols identify the proxy loaded in this process. On a V100,
a program can prefer its native Volta kernels, including PTX for `sm_70` that the
driver compiles directly. The
launcher sets `VOLTA_FOREVER` (the version) and `VOLTA_FOREVER_HOME` in the
environment of what it runs, for scripts.


## 5. Launch

### What happens at a launch

Kernel launches (`cuLaunchKernel`, `cuLaunchKernelEx` and their forms for the per-thread
default stream, `cuLaunchKernel_ptsz` and `cuLaunchKernelEx_ptsz`) go through the proxy when it
adapts code (the default), when the second translation at launch is on (`VF_FIT`, the default),
or when statistics, the profile or the trace of launches are asked for; with `VF_ADAPT=0
VF_FIT=0` and none of these, lookups of these functions return NVIDIA's own pointers. For a
launch that the driver accepts, the proxy's entry calls the driver and returns its answer.

### A launch of a refused kernel

A launch of a kernel that the layer refused, with a handle that the program holds all the same
(section 3, "What is refused"), returns `CUDA_ERROR_INVALID_PTX` (218), the error of the lookup
of that kernel, and is not made; a line says why, once for each kernel. The cause is the one of
the refused lookup, the code of that kernel cannot be made for this GPU, and the program gets the
same answer; the context stays usable (the next kernel runs). NVIDIA's driver answers
`CUDA_ERROR_INVALID_HANDLE` (400) to a launch of a handle that is no function (measured with a
null one), which would tell the program that its handle is wrong.
The same holds for every launch of the driver's interface (the four above,
`cuLaunchCooperativeKernel` and its form for the per-thread default stream,
`cuLaunchCooperativeKernelMultiDevice`, `cuLaunch`, `cuLaunchGrid`, `cuLaunchGridAsync`), for a
kernel node of a graph made or changed with such a function or kernel (`cuGraphAddKernelNode`,
`cuGraphKernelNodeSetParams`, `cuGraphExecKernelNodeSetParams`, both versions of each,
`cuGraphAddNode`, `cuGraphNodeSetParams`, `cuGraphExecNodeSetParams`: a graph launches its
kernels later, where nothing can be refused; a node that names a library's kernel and a context
is judged for the device of that context), for what is asked about it or set on it
(`cuFuncGetAttribute`, `cuFuncSetAttribute`, `cuFuncSetCacheConfig`,
`cuFuncSetSharedMemConfig`, `cuFuncGetParamInfo`, `cuFuncLoad`, the four of `cuKernel...`, the
seven occupancy functions), and for `cuKernelGetFunction`, which also leaves NULL in the handle.
What is not covered: a kernel launched by another kernel, a function reached from a kernel by an
indirect call or across inputs of a link (it still traps), and a launch through a private table
of the driver (cuFFT launches with `cuLaunchKernel`).

What a handle is takes calls of the driver and a lock. It is asked once for each handle in each
generation of the layer's records; what was found allowed is kept in a table read without a lock
(4,096 sets of four slots, by a hash of the handle; a slot holds the handle and the whole
generation it was found in, with a version that a writer makes odd). A generation ends whenever
the records of refusals change, at every load and every unload of a module or a library, and
whenever a context goes (an unload and a context that goes end two: one before the driver's call
and one after), so a program that loads code as it runs asks again after each load: over the 925
cases of `tests/gpu/torch.sh`, run by one process, the driver was asked 1,380 times in 911
generations, for 5,992 launches by `cuLaunchKernel` (`VF_STATS`, which says at exit how many times
the driver was asked, how many calls were refused and how many generations there were). A question
costs 1.4 to 2.0 microseconds more than the launch: the first launch of each of 2,000 kernels in
turn took 3.7 to 4.2 microseconds, against 2.3 without the refusal, and the launches of the next
turns as much as without it (2.15 to 2.20, `launch_rate many-refusing`, two rounds alternated with
the build before, 2026-11-23). While no module or library has a refused kernel, nothing is asked
and a launch costs one load of a counter more; otherwise a launch of a handle already seen costs a
few loads: the counter, the generation, and the slots of its set. Measured on a V100 (one session,
three rounds alternated, 2026-11-23; `tests/kernels/launch_rate.c`, the median of 2,000 bursts of
64 launches of an empty kernel): one `cuLaunchKernel` call takes 2.20 to 2.23 microseconds on the
CPU through the layer before the change and 2.23 to 2.25 after; with a module with a refused kernel
loaded, 2.23 to 2.28 before (where it changes nothing) and 2.23 after; through NVIDIA's driver
alone, 2.19 and 2.22 (another session). In a loop of 40,000 small PyTorch operations (60,003
launches; PyTorch's libraries have refused kernels), the driver was asked what a handle is 4 times.

### A second translation for a kernel that does not fit

The largest block a kernel may be launched with follows from the number of registers
its code declares. Measured on a V100 (driver 580.178.04) by patching the count of a
kernel and launching it at every block size: registers are given in groups of eight
per thread, and the limit is `min(1024, 128 * floor(512 / n))` threads for a count
rounded up to `n`: 1,024 threads up to 64 registers, 896 for 65 to 72, 512 at 128, 256
at 255. The usual translation of machine code adds registers of its own above the
kernel's; that may take a kernel compiled for blocks of 1,024 threads past 64. The
driver refuses nothing when the module is loaded: it refuses the launch
(`CUDA_ERROR_LAUNCH_OUT_OF_RESOURCES`, error 701), and only for the blocks that are
too large.

When this happens, for a kernel of a module whose machine code the layer translated,
the proxy translates the module's image again so that no kernel takes more registers
than it declared, rounded up to a multiple of eight (uniform registers are then kept
in the thread's local memory: slower code; `docs/translator.md`, "Registers"), loads
that as a module of its own, and launches the kernel from there
(`crates/vf-proxy/src/fit.rs`, `VF_FIT`, on by default).

Every launch still goes to the first translation first: a smaller block may fit it,
and it is the faster code. The refused call costs about 1 microsecond.

A kernel that requires one block size (PTX's `.reqntid`, which Triton writes for every kernel) has
no smaller block, and a program may read the largest block the loaded kernel allows before it
launches (Triton does, and stops when it is smaller than its own). Such a kernel is not left to
this: its first translation keeps within the registers of that block, or it is refused for its
registers and the layer runs the PTX that its cubin keeps (`docs/translator.md`, "A kernel that
requires its block size").

**What the program set on the kernel.** The settings that the program made
(`cuFuncSetAttribute`, `cuKernelSetAttribute`, the cache configuration) are made on the
kernel of the second translation too, when it is taken and whenever the program makes
one after. A library's kernel and the function of the same name in the module that the
driver gives for the library are one kernel to the driver (measured on a V100): what
`cuKernelSetAttribute` sets on the first holds for the second in a context of that
device, unless the function has a setting of its own for that attribute, whatever the
order of the calls. The second translation of such a function is a function of a module:
it is given, with `cuFuncSetAttribute`, the library kernel's settings for the device of
the current context, then the function's own; a setting of the library's kernel that
comes later is given at the next refused launch, where the function's context is
current. The other way round is not done (`LIMITS.md`). A setting is one step: the
driver's call on the program's kernel, what the proxy remembers of it and the same call
on the second kernel are made under one lock, so that two threads which set the same
thing at once leave the kernel and its second translation with the same value.

**Safety rule.** A kernel that can reach data of its module (determined from its
relocations) is never launched from a second translation: the second module has its
own copy of the data, which nothing keeps in step with the first's. Nor is any kernel
of a module from which the program asked for a variable, or for a texture or surface
reference, by name: by either exported name of the call (`cuModuleGetGlobal`,
`cuModuleGetGlobal_v2`), by what `cuGetProcAddress` gives for it, through a library
(`cuLibraryGetGlobal`, `cuLibraryGetManaged`), or through the module that the driver
gives for a library, which is the library's image under another handle. The driver's
first answer is returned to the program. No launch into a second translation starts
after the program was given such data: the launch is made under a lock that the
exclusion takes alone, after looking again, and a launch whose second translation was
being made when the program asked gets the first answer too.

In a stock PyTorch 2.14.0, the operations of the test battery that need this
mechanism are `avg_pool2d` and `interpolate` in float32 and float64, and `unfold` in
float32 (blocks of 1,024 threads whose usual translation takes 66 registers), and
three of the 32 small whole models. With `VF_FIT=0` those launches are refused to
the program. The mechanism covers the four launch entries (`cuLaunchKernel`,
`cuLaunchKernelEx`, and the two for the per-thread default stream), and kernels taken
from a module, from a library by name or by enumeration, or from the module that the
driver gives for a library. It does not cover a launch recorded in a CUDA graph (it
fails later, where there is nothing to try again), a kernel that the program launches
through a function handle made from a library's kernel (`cuKernelGetFunction`), nor
the old launch functions (`cuLaunch`, `cuLaunchGrid`). The independent validator
checks second translations as it does the usual ones (`docs/validation.md`, "The
corpora").


## 6. The CUDA 13 libraries

CUDA 13 math libraries (cuBLAS, cuBLASLt, cuFFT, cuSOLVER, cuSPARSE, cuRAND, NPP,
nvJPEG, NVRTC) hold no Volta kernels and refuse sm_70 devices. Their CUDA 12.9.2
builds still have Volta code. The layer puts 22 generated forwarding libraries in
front of the 12.9 originals, one for each library a program asks for by its CUDA 13
name.

### How calls are forwarded

Each forwarding library has the same SONAME, the same exports (names, symbol
versions, version definitions) as the CUDA 13.5 original
(`crates/vf-fwdgen`, `scripts/build-forwarders.sh`).

Each function is a jump: `endbr64; mov slot(%rip),%r11; test; jz slow; jmp *%r11`.
Stack arguments, structures passed by value, callbacks and the floating-point
argument-count register pass untouched (no prototype is needed for the 99 % that are
forwarded as they are). The first call of a function enters a common routine that
saves the argument registers and SSE registers, calls `dlsym` to find the 12.9
function, stores its address and jumps. Two threads reaching the same first call both
store the same address.

The 12.9 library is opened by SONAME through `dlopen` at the first call of any of
its functions, never at load time. This way a program that links the library without
using it pays nothing.

### What differs between the two interfaces

Of 9,710 exports across the 22 libraries:

- **9,492** forward as they are (6,768 of these with the returned NPP status
  renumbered: NPP changed the numeric values of its error codes between 12.9 and
  13.5).
- **49** are adapted (renamed functions, changed prototypes: cuBLASLt's stream
  arguments, cuFFT's JIT callback, the NVRTC builtins).
- **169** are stubs: functions that CUDA 12.9 lacks return the library's
  "not supported" status and say so once on the console (emulation-related accessors,
  grouped-GEMM layout in cuBLASLt, sparse-matrix operations in cuSPARSE, the NPP
  workspace API).

The status-renumbering stubs copy the caller's stack arguments to their own frame
before calling the 12.9 function. The number of stack words is computed from each
function's prototype following the System V x86-64 calling convention exactly:
integer and pointer arguments fill the first six integer registers, floats and doubles
the first eight SSE registers, and what remains goes on the stack. Structures by value
are classified by compiling a GCC probe.

### What is not supported

The 169 stubs are for functions that CUDA 12.9 does not have. `dist/forward/REPORT.txt`
lists every export and its treatment. A program that calls one gets the library's
"not supported" code and a one-time message on the console.

The forwarding libraries do not redistribute NVIDIA's code: they are generated
entirely from the export lists and headers of the two toolkit versions
(`vf-fwdgen generate`). The CUDA 12.9.2 libraries themselves are downloaded
separately by `scripts/fetch-redist.py` from NVIDIA's public redistributable
archives.

### The bf16 variants of cuBLAS and cuBLASLt

`forward/bf16tc/` holds an opt-in pair beside the default forwarders: `libcublas.so.13` and
`libcublasLt.so.13`, generated by the same code (`crates/vf-fwdgen/src/bf16.rs`) with the same
exports, versions and SONAME, and one runtime that both load, `libvf_cublas_bf16.so`. The default
forwarders are not touched: their bytes are 0.1.3's. The launcher maps both CUDA 13 names to the
variants together when `VF_CUBLAS_BF16_TC` or `VF_CUBLAS_BF16_SKINNY` is `1`, and refuses to run
when one of the three files is missing; without the launcher the variables do nothing.

- **Binding.** A variant forwards every function as the default one does, except handle creation and
  destruction, `cublasSetStream_v2`, `cublasSetWorkspace_v2`, `cublasGemmEx[_64]`,
  `cublasGemmStridedBatchedEx[_64]` and `cublasLtMatmul`. These jump through slots of their own,
  bound at their first call: to the runtime's `vf_bf16_<name>` when a switch is set and the runtime,
  found beside the variant (`dladdr`), loads and says it serves; else to CUDA 12.9's function. A
  runtime that cannot be loaded is said once and every call is forwarded.
- **One state for both interfaces.** The runtime keeps a table of handles of both kinds (a
  `cublasHandle_t` may be used as a `cublasLtHandle_t`), read without a lock under a sequence
  counter; each gives the state of the context it was made in (`cuCtxGetId`) and, for a legacy
  handle, whether its workspace is cuBLAS's default or at least 4 MiB.
- **Per context**, nothing is made when a handle is created. The first call that a path would serve in
  a context makes what that path needs there, never freed while the process lives: for both paths the
  module of the checked-in fat binary (`crates/vf-fwdgen/bf16tc/kernels.fatbin`, sm_70 machine code)
  with every function loaded (`cuFuncLoad`) and its launch configuration checked; for the tensor-core
  path, at its own first call, a memory pool and a cuBLASLt handle of the runtime's own for the internal
  fp16 GEMM. That call may come inside a graph capture, so all of this is made in relaxed capture mode
  for the calling thread, and its mode is given back. A context that is not a V100's, or whose kernels
  do not load, forwards every call from then on. The runtime's file holds sm_70 machine code, so the
  proxy tells it the real capability whatever `VF_CAPABILITY` says (section 4).
- **A call.** Every decision that can forward it is taken before anything is enqueued: the types, an
  explicit algorithm (forwarded), the sizes, the handle's context against the current one and the
  stream's, the math and pointer modes (read once), aliasing of the output with an input, the path
  (`docs/emulations.md`, section 11), and whether a tensor-core call is captured. The internal GEMM runs on the runtime's cuBLASLt handle, with the stream read once, descriptors of its
  own, host scalars and no workspace: nothing another thread changes on the caller's handle reaches
  it. A launch refused after the output was written returns `CUBLAS_STATUS_EXECUTION_FAILED`; before,
  the call is forwarded.
- **Graph capture.** A tensor-core call allocates its workspace (at most 32 MiB) on its stream. In a
  capture that allocation would become an allocation node of the program's graph, and a graph that
  holds one cannot be instantiated twice, embedded as a child graph, instantiated for device launch,
  updated from a recapture, or instantiated at all when it was captured into a conditional node's body
  (`tests/gpu/forward/bf16-graphs.c` with `VF_BF16_CONTROL=capture-tc`, a test build's control that
  serves captured calls), none of which the runtime can see coming when it is called. So a captured
  tensor-core call goes to cuBLAS 12.9, and the same test checks that a graph captured through the
  variant then behaves step for step as with 12.9 alone. The skinny path serves captured calls: it adds
  one kernel node and allocates nothing. An eager call's allocation is made in relaxed capture mode
  for the calling thread (`cuThreadExchangeStreamCaptureMode`), so that it cannot invalidate a capture
  of that thread or another's in global mode.
- **Statistics** are counted on the host, and said at exit with `VF_LOG_LEVEL=2`: per entry point,
  the calls each path served and the forwarded ones by reason.

### The audit library

Programs that open libraries by absolute path or through RPATH (a stock PyTorch
wheel, ZML) are not reached by `LD_LIBRARY_PATH`. The audit library
(`crates/vf-audit`, `dist/lib/libvf_audit.so`) intercepts the loader's
`la_objsearch` for every `dlopen`, including absolute paths, and substitutes
libraries by file name from a map (`VF_AUDIT_MAP_FILE` or `VF_AUDIT_MAP`).

One setting is not a library: `@cudnn-version=9.24.0` makes cuDNN's
`cudnnGetProperty` and `cudnnGetVersion` answer that version, so a program whose
minimum-version check would refuse the older cuDNN that has code for Volta accepts
it (ZML needs this).

### The nvJitLink adapter

Programs whose JIT stacks compile through nvJitLink 13 (XLA in ZML, Triton in vLLM
and SGLang) need an nvJitLink that accepts the code and can target sm_70.
`crates/vf-jitlink` (`dist/lib/libnvJitLink.so.13`) presents the CUDA 13.5
nvJitLink API and serves it with nvJitLink 12.9.2:

- `-arch=sm_75` (or higher) becomes `-arch=sm_70`.
- PTX inputs are adapted the same way as in the proxy: header lowered to ISA 8.8
  (the 12.9.2 ptxas limit) and `.target` to sm_70, Turing-only instructions rewritten.
- Raw cubins must target sm_70. For host objects and static archives the CUDA 12.9 linker
  selects their embedded device code for the requested target.
- Options only in 13.5 (`-Ofc`, `-nvvm-latest`, `-no-cache`, `-device-stack-protector`) are
  dropped silently.
- A null array of options, a null option, and an input of no bytes or at a null address are
  refused with `NVJITLINK_ERROR_INVALID_INPUT`, as nvJitLink 12.9.2 does.


### The launcher

`scripts/vf` (`bin/vf` of an archive; `volta-forever` is a link to it) puts the parts
together for one command: the library path (the proxy and the nvJitLink adapter, the
forwarding libraries, the CUDA 12.9.2 libraries), the audit library with a table that has, for
each forwarding library, its name and the name of the library that it calls, and the two
variables that say the layer is there; for the command it runs, also `VF_CUDA12` and, for a Bazel program, `RUNFILES_DIR` (`INSTALL.md`, "What the launcher sets"). It keeps the audit libraries that `LD_AUDIT` already names, after its own, and refuses an installation or a CUDA 12.9.2 directory whose path has a `:`. The audit table also selects the VF nvJitLink adapter when an application bundles CUDA 13's linker under the same name and gives that directory priority through an ELF RPATH. A forwarding library is used
only when the CUDA 12.9.2 library that it calls is there: without it the program keeps its
own library of that name, whose kernels the layer translates like the rest of the program's
code (cuBLAS is the one that a program cannot keep: the translator refuses some kernels of
its CUDA 13 build). `vf venv` puts in a virtual
environment of Python a module that each of its Pythons imports when it starts and that
starts it again through the launcher, so that the environment runs through the layer with no
prefix: pip too, and with it a build that asks the GPU what to compile for. `INSTALL.md` has
the launcher's use and what it does by hand.


## 7. Switches and diagnostics

The layer is controlled by environment variables. `INSTALL.md` ("Environment variables") has
each of them once, with its default, its values and the library that reads it; here they are
grouped by what they control.

### Logging

`VF_LOG_LEVEL`, `VF_LOG`, `VF_EMULATION_WARNINGS`: what the proxy, the audit library and the
nvJitLink adapter say, and where.

### Translation control

`VF_TRANSLATE` (whether machine code is translated, and where PTX or sm_70 code exists too),
`VF_BORROW` (where the translation of machine code takes the registers it needs:
`docs/translator.md`, "Registers"), `VF_PAIRS` (pairs of products on whole rows:
`docs/pairs.md`), `VF_ALIGNED_ROWS` (whether the rows that `ldmatrix` reads are taken to be
at multiples of 16 bytes).

For a CUDA graph that fails at instantiation with `CUDA_ERROR_LAUNCH_OUT_OF_RESOURCES`,
try `VF_BORROW=9 vf ./program`. A graph can record a launch before the driver checks its
registers. The ordinary launch-time retry has no opportunity to select a second image here.
Mode 9 keeps the default translation, including its register borrowing, unless it excludes a block size
allowed by the source kernel on GV100. In that case it selects a bounded placement during
module translation if that placement restores the full block size. Required and maximum block dimensions in the cubin limit this
check. Entries with code relocations or jump tables keep their ordinary layout. A kernel that needs borrowing can run more slowly with small blocks. When no bounded
placement restores the full size, the driver receives the default translation.

### Image adaptation

`VF_ADAPT` (images given to the driver unchanged), `VF_LAZY` (each kernel compiled when it is
asked for, or whole modules when they are loaded: section 3), `VF_CAPABILITY` and
`VF_CAPABILITY_ALL` (what callers are told, and so which PTX is taken: section 4), `VF_FIT`
and `VF_FIT_SHARED` (the second translation at launch, and the retry of a dynamic shared
memory setting at the V100's limit: section 5), and the opt-in BF16 paths of the PTX
rewriting, `VF_BF16_TC_GROUPS`, `VF_BF16_TC_TILES`, `VF_BF16_COLUMN`, `VF_BF16_ROW`
(`docs/emulations.md`).

### Cache

`VF_PROXY_CACHE`, `VF_PROXY_CACHE_MAX`: where the cache of section 3 is, and how large it may
grow.

### Diagnostics

`VF_STATS` (call counts, the kernels launched most, and what the refusal of a kernel at its use
asked the driver and refused), `VF_TIMING` (the time of each stage),
`VF_PROFILE` (a profile of each kernel; every launch is synchronised on its stream, so a
profile is not a benchmark), `VF_TRACE_LAUNCH` (the launches that the driver refuses),
`VF_TRANSLATE_DUMP` (every cubin given to the translator, for offline validation),
`VF_BORROW_SAY` (what the translator borrowed), `VF_REAL_LIBCUDA` (where NVIDIA's library is).

### Audit and nvJitLink

`VF_AUDIT_MAP`, `VF_AUDIT_MAP_FILE` (the substitutions of the audit library), `VF_JITLINK_REAL`,
`VF_JITLINK_REAL_DIR` (the nvJitLink 12.9 behind the adapter), `VF_JITLINK_DUMP` (its PTX
inputs as the program gave them), and for the forwarding libraries `VF_FWD_<KEY>` and
`VF_FWD_VERBOSE`.
